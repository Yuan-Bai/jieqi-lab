# GUI 棋谱研究与摆棋（更新于 2026-10-11）

## 规则与算法适配

GUI 使用 `jieqi.py` 的当前规则 v5。暗子按假类型走子后翻开，暗士限九宫、暗象不过河；明士/象无区域限制。
捕获暗子的真实类型只进入吃方的信念，原主只知道总数减少。长将/长捉跟踪同一枚棋子，阈值 6 回合；
公开局面第三次重复或 80 ply 无吃子判和，将死/困毙优先。GUI 不另写一套合法性判定。

现有 RIS 和 AZ 搜索均在根信息下逐模拟确定化一次，再由合成行动者观测连接共享决策统计。
AZ 使用当前 238 通道编码、PUCT 与机会节点（`chance_nodes=True, chance_k=0`）。GUI 继续调用现有
`load_model_if_exists`，旧 64/71 通道权重由算法层补零加载。GUI 加载纯权重 `latest.pt`/`best.pt`，
完整训练检查点应由训练入口恢复。棋力、模型校准及信息集近似的限制仍以算法报告为准。

本次未修改 `azero.py`、`ismcts.py`、`jieqi.py` 或训练产物。

棋谱列表的连续走子竖直排列，不随步数逐层缩进；只有真实分叉新增展示层级。
各变例按顺序展示完整后续走子，点击回看及上一步仍按真实棋谱节点导航。

## 修复与功能

| 原行为/问题 | 当前行为 |
|---|---|
| 回放禁用保存、分析和走子 | 可保存整个棋谱、计算胜率/提示、直接走子添加变例 |
| 线性走子列表、固定标准起局 | 棋谱树、完整起始局面，支持摆棋和多级分叉 |
| 分支不存在 | 下一步遇到分叉只展示编号；选择后才推进，结尾也不跨过未选择的分叉 |
| 用步数/行动方判断分析是否过时 | 棋谱实例、节点、模型文件时间/大小、配置与任务代次共同隔离结果 |
| 旧分析仍运行，新局面不一定重新分析 | 每通道一个工作线程、一个待办，最新请求替换旧待办；模拟边界协作取消 |
| 工作线程闭包持有 GUI 控制器 | 引擎池与 Tk 对象分离，避免关闭后在工作线程析构 Tk 对象 |
| AI 对战两方都选 RIS 时，胜率模型选择器隐藏 | 开启 AI 胜率时也展示模型选择器 |
| 未知被吃被重复扣减到暗池总数文案 | 剩余暗子数与未知被吃类型数量分别显示 |
| 固定窗口可能裁切小屏幕底部 | 小屏幕提供滚动条，保证操作可访问 |
| 调整 AZ 搜索预算可能重复载入模型 | 同模型在通道内复用，逐次显式传入模拟次数 |
| GUI 无法选择 AZ 叶批大小 | 开局及对弈中可分别设置红黑参数，分析可独立设置 |

提示和胜率默认 200 模拟，可独立于对弈预算修改。分析与对弈各持有一个串行工作通道及独立引擎/RNG；
人类操作不等待分析。缓存只保留在当前 GUI 会话中，重新加载棋谱可用选定模型重新计算。
取消发生在模拟/随机采样边界；正在执行的模型加载或 GPU 前向会先完成。
上帝视角只改变界面显示，分析仍按当前行动方已知信息计算，不能预知自己被吃的暗子真实类型。

## 运行时调整 AZ 叶批大小

- 开局：选择 AlphaZero 后设置「叶批大小」；AI 对战分别设置「红方叶批」「黑方叶批」。
- 对弈中：棋盘下方「对弈叶批量」可修改正在对弈的 AZ 一方或双方。
- 提示、胜率与棋谱研究：右侧「分析设置」中的「叶批大小」独立控制分析搜索。

默认仍为 64，提供 1/8/16/32/64/128 选项，也可输入 1～100000 的整数。
算法按模拟次数限制有效批大小，末批、终局及叶去重还可能减少实际网络前向数量。
叶批是搜索参数，与训练优化器的 `batch_size` 无关。较小叶批可能增加搜索耗时；
冻结模型的固定模拟次数对照不能直接证明固定时间或续训收益。

算法已有接口：`AZConfig.leaf_batch_size` 可修改，`NeuralMCTS.search()` 在每次搜索开始时读取它。
GUI 在各串行工作通道的下一次搜索开始前更新配置，复用已加载的同模型，不修改正在运行任务的配置。
应用新参数会协作取消并丢弃旧任务结果，对弈按当前局面重算；暂停时保留暂停状态。
分析缓存包含叶批大小，避免把旧批量的胜率当作新批量结果。双方对弈参数与分析参数互不覆盖。
棋谱、走子、分支和训练配置不因调整叶批而改变；设置保留在当前 GUI 会话中。

## 棋谱 v2

`game_record.py` 管理节点及持久化，Tk 只负责展示。保存的 JSON 包括：

- `initial.state`：棋盘整数编码（保留任意格暗子的假类型）、先走方、真实暗池、规则配置、
  无吃子计数、将/捉跟踪字段、完整公开重复历史、可选预分配暗子映射。
- `initial.belief`：双方池计数、总数、未知被吃量及公共账本；`initial.captured` 保留起点吃子记录。
- `nodes`：从 1 起连续编号，父节点必须已出现；根隐式编号为 0。每条边的 `move` 含
  `from/to/reveal/capture/uci`。不同变例分别从父快照重演，状态、信念与规则历史互不改写。
- `cursor`：保存时的当前节点；其余元数据保留参与方与观看视角。`end` 表示当前节点的规则结果。

v1 读取后转换为单链，保存写 v2。旧 v1 文件不会自动改写。加载先完整验证棋谱，再替换界面；
损坏文件、未知规则版本、缺失揭示、非法着法、无效节点关系均拒绝加载，当前棋谱保留。

文件包含完整私有捕获记录，延续原棋谱的保存语义；观看时按原玩家/观众视角过滤。
对弈或回放保存的是全部分支，零走子局面也可保存。保存取消或失败不会清除未保存状态。
没有预分配暗子身份（`dark_types=None`）时，新变例从暗池独立抽样；同一枚暗子在两个新走法分支中
可能翻出不同类型。已有边复用记录结果。这些分支表达走法与机会结果，不能当作同一副固定暗子布局的纯走法对照。
GUI 研究棋谱不会自动进入自博弈训练缓冲。相关私有信息对照见 [2026-10-05 检查报告](reviews/2026-10-05-gui-replay-information-audit.md)。

## 旧规则棋谱兼容

GUI 自动对规则 v3/v4 的 v1/v2 棋谱执行内存迁移：每条边按 v5 的合法着法、终局和将/捉跟踪重新计算，
继续使用记录中的翻子与暗子捕获结果，保留全部分支、私有信念及当前节点。界面标明原规则版本。
不能通过当前裁判的走子会报出手数；树格式还会报出节点编号，不跳过或随机补造着法。

保存迁移后的棋谱使用当前规则版本，`rules_migrations` 保留来源/目标规则版本及原 `end`；
新的 `end` 按当前节点重新计算。再次加载不重复迁移，继续走子产生的分支随整棵树保存。
加载不会写回来源文件，仅用户执行保存时写入所选文件。

对于从中途局面开始的旧 v2 棋谱，起点之前的将/捉身份无法从快照恢复为 v5 的语义。
若起点含这些旧跟踪字段，则从起点重新计数，并在界面明确提示；原字段保存到迁移记录中。
棋盘、暗池、私有信念、无吃子计数及公开重复历史继续保留。标准起局的棋谱不涉及此重置。

`GameRecord.from_dict()` 默认仍严格要求当前规则；只有 GUI 显式启用 `migrate_rules=True`。
训练数据、完整续训的规则门禁没有更改，也不能把棋谱迁移当作旧训练数据的重标版本许可。

## 摆棋

编辑器中点击放置、右键移除；明子和暗子分开设置，暗子兵种表示行棋假类型。
暗池各类型数量表示未翻开的真实组成，没有绑定到具体格；首次走子/捕获时按池抽取并记录。
将帅各一个且在九宫内，不能是暗子；明子和暗池同类型总数不得超过标准数量，暗池合计必须等于棋盘暗子数。
遗漏棋子视为已吃，编辑器中的起始暗池组成视为双方已知；应用后重新开始计将/捉/重复历史。

从已有局面打开编辑器仅编辑副本，取消后恢复原来的暂停状态。应用为新棋谱前可保存原棋谱。
右侧「从此对弈」可指定人机执红/执黑或 AI 对战，原有分支保留。
