# 编译后自博弈多局面热点剖析（2026-10-05）

结论：攻击判定编译后，下一阶段应优先实验 **节点扩展及初始化的精确加速**，
而不是把全部规则或 MCTS 一次性搬到 Cython。较低扰动的 8-worker 函数边界测量中，
`PUCTNode.expand` 占累计搜索时间约 33%–34%；合法着查询约 11%，其中仍包含原生攻击
查询及逐调用计时的额外开销。合法着快路编译有价值，但现在不是最大热点。

本次仅新增独立剖析工具、工具测试及本报告，未修改规则、MCTS、训练参数或原生二进制。
检查点、模型、状态、日志和最近 replay 前后 SHA256 均未变化；生成的诊断对局未加入训练。

## 测量方法与开销

第一轮每根/预算先预热一次，再测 plain、cProfile、边界计时和第二次 plain。
两次 plain 分别位于插桩测量前后。48 个根/预算组合分别对照结果，并在预热的
8-worker 池内做两组交替顺序的 plain/边界配对。

第二轮只计 `expand`、`select_child` 和根/叶评估的大函数边界，不在每个构造函数或
攻击调用上插桩；8-worker 池做四组交替顺序配对。它用来确认 cProfile 的扩展热点
不是仅由数百万次小函数的 profiling 回调放大出来。

| 串行测量，24 根合计 | 普通800 | strong3200 |
|---|---:|---:|
| plain，两次合计的平均 | 9.951s | 40.712s |
| cProfile | 15.635s | 71.137s |
| cProfile 相对增时 | 57.1% | 74.7% |
| 规则/评估边界插桩 | 10.525s | 45.828s |
| 规则/评估边界相对增时 | 5.8% | 12.6% |

第二轮 8-worker / 24 根的平均组墙钟：plain=1.956/8.035s，插桩=2.006/8.295s，
对应增时 2.6%/3.2%。单对增时范围分别为 -1.2% 至 +5.7%、+0.7% 至 +10.2%，
包含调度和持续频率变化；这些数字不能视为精准扣除的固定计时器成本。

当前扩展没有 Cython 内部 profiling hooks，cProfile 统计中根本没有攻击判定条目；
其时间可能落在 Python 调用者的 own time 上，不能解读为原生调用耗时为零。
cProfile 的自身开销也偏向 Python 小函数。函数 cumulative time 有嵌套，不能逐项相加。
依据：[Cython profiling 文档](https://docs.cython.org/en/latest/src/tutorial/profiling_tutorial.html)、
[Python 3.11 profiler 文档](https://docs.python.org/3.11/library/profile.html)。

## 热点结果

以下百分比的分母是对应插桩搜索的 **累计 worker 墙钟时间**，不是进程池组墙钟、
纯 CPU 利用率或 GPU kernel 占比。不同探针的行不能相加。

| 第二轮较低扰动函数边界 | 普通800 | strong3200 |
|---|---:|---:|
| `PUCTNode.expand` | 33.50% | 34.05% |
| `PUCTNode.select_child` | 2.88% | 4.06% |
| 叶批评估 | 35.91% | 32.03% |
| 根评估 | 1.80% | 0.43% |

每组 24 根，扩展耗时为 4.753/20.463 worker-seconds，扩展调用为 16419/67764 次。
扩展包括策略归一化、着法索引、机会结果完整枚举、节点初始化和字典插入，
**不是纯内存分配时间**。边界也可能包含线程被抢占的等待，不能据此推断所有时间都
能通过 Cython 消除。

| 第二轮按材料阶段拆分 | 普通扩展 | strong扩展 | 普通叶批评估 | strong叶批评估 |
|---|---:|---:|---:|---:|
| 开局 | 43.12% | 44.97% | 29.69% | 26.03% |
| 中盘 | 23.75% | 23.23% | 42.39% | 37.83% |
| 残局 | 9.29% | 8.76% | 50.47% | 46.88% |

仅看 18 个真实模型轨迹根，扩展占比仍为 34.50%/35.65%；结论并非受控残局造成。
cProfile 记录普通/strong 共创建 2,102,094/8,299,872 个 `PUCTNode`；三个初始根各自约
23 万/86 万节点。暗子多、chance_k=0 的完整机会分支使开局扩展显著更贵。
构造函数 own time 在 cProfile 中约占 11%，但该比例受小函数插桩影响，不作为生产
“纯分配比例”。节点扩展和构造函数 cumulative time 也不能相加。

| 第一轮 8-worker 规则/输入边界 | 普通800 | strong3200 |
|---|---:|---:|
| 合法着查询，含攻击调用 | 10.73% | 11.43% |
| 原生攻击函数体，全部调用 | 2.53% | 2.75% |
| 原生攻击函数体，位于合法着查询内 | 2.29% | 2.42% |
| 合法着查询减去其中原生函数体 | 8.44% | 9.01% |
| 编码，已嵌套在评估内 | 5.30% | 5.82% |
| 叶去重签名 | 0.94% | 1.35% |

“合法着减原生”仍包含数百万次原生调用的 Python 包装及计时开销，只是本次插桩里
剩余的预算，不是生产中可兑现的加速比例。串行规则查询占比约 8.8%/8.7%，
扣原生后约 6.8%/6.8%，进一步说明不能把规则微测倍数直接换算为整轮收益。

评估包含编码、传输、CUDA 网络/softmax、同步等待及输出回传；编码和评估不相加。
cProfile 的 `Tensor.cpu()` own time 约占 15%/20%，这包含等待先前 GPU 工作完成，
不是纯 D2H 带宽开销。因此当前资料不足以断言“集中推理能省这全部时间”。

## 下一阶段建议

1. 优先给 `PUCTNode.expand` 与初始化做小范围精确编译实验；先保留 Python 节点/字典
   和现有接口，按调用结构验证真实收益，再决定是否扩展范围。
2. 保持完整机会概率支持、枚举顺序、Python 浮点运算次序、平分时的选择顺序、RNG
   流和节点状态隔离。不能仅凭吞吐通过就接入默认自博弈路径。
3. 以同根策略字节、着法、RNG、完整树图、叶/机会计数、完整对局样本及双后端回归
   验收；配对测试以当前已优化 Python/Cython 混合版本为基准。
4. 合法着快路编译列为第二优先。它边界较清晰，但剩余预算较小；继续保留禁着慢路
   与生成器恢复时机，先做定向规则对照。
5. 集中 GPU 推理、worker 数量扫描仍需独立实验。它们涉及调度、batch 形状和 CUDA
   数值边界，不与本次精确热点编译混在一次改动中。

这里给的是下一实验的优先级，没有承诺具体加速倍数，也没有实现下一阶段。
后续已完成上述小范围节点方法编译实验：等价性通过，但没有可靠的整体加速收益，
因此默认仍用 Python 节点方法，见 `docs/reviews/2026-10-05-native-search-experiment.md`。
两种预算在池中分别运行，strong-only 并发不代表实际 1/8 strong 的混合生产负载；
24 固定根还包含跨进程传输，不能用其组墙钟推算完整 1024 局或等棋力收敛速度。
