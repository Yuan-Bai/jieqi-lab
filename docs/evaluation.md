## 对手选择

- `model:<path>[:sims]`：冻结的历史模型，建议包括近期冠军和两个较早里程碑。
  对比时核对规则版本、权重哈希及原训练来源；旧权重能加载不代表训练来源一致。
- `pika:<budget>`：外部 Pikafish **jieqi_old**。`--pika-limit nodes` 表示节点预算，
  `--pika-limit movetime` 表示每步毫秒。缺省预算 10000，线程 1、Hash 32 MiB。
- `ris:N` / `random`：固定回归基线。修改 RIS 实现后应另起基准版本。

优先分别报告各对手得分，而非把随时变化的对手池压成一个不可比的平均分。
固定参照长期保留，近期冠军单独滚动；评估池引用带哈希的冻结副本，不能使用会变化的 latest/best 路径。
日常 100 局/对手仅作信号检查；正式确认按预先约定的局数和区间宽度制定预算，
保留未用于调参的验收种子，避免看到有利结果就提前停止。

已准备候选模型与自己的冻结池清单后可运行（默认生成唯一输出路径）：

```powershell
python tools/eval.py --model data/models/latest.pt --pool data/eval/my_pool.json --games 100 --sims 1600 --leaf-batch-size 16 --workers 8 --seed 2026102202
```

清单 [eval_pool_20261022_1600_leaf16.json](../configs/eval_pool_20261022_1600_leaf16.json)
记录原三个历史权重的引用（权重未分发），固定双方1600模拟、叶批16及完整SHA256。权重路径相对清单目录解析，规则版本/文件/哈希不符即报错，
不会静默换成 RIS。迁移机器需复制忽略在 Git 外的三个权重及来源记录。
`--pool` 与 `--opponents` 互斥，也不能与 RIS 专用 `--quick` 合用。
新清单的 `search` 固定双方基准；命令行/训练配置与它不一致会在开始对局/训练前报错。
旧 [800模拟清单](../configs/eval_pool_20261022.json) 原样保留，复查旧基准需显式
`--sims 800 --leaf-batch-size 64`（训练为 `--eval-mcts-simulations 800 --eval-leaf-batch-size 64`）。
不使用清单而直接指定 `model:path` 时，对手未写模拟数后缀则继承候选的 `--sims`；
双方模型均使用 `--leaf-batch-size`。RIS/Pika自己的迭代/节点预算另行指定，不套用模型模拟数。

## 对手怎样选、怎样更新

当前是**手动确定、固定全量评估**的三模型池，不按胜率随机抽样，也不自动扫描新的checkpoint：

| 固定权重 | 当前角色 | 选择依据与边界 |
|---|---|---|
| `ris_best_iter50.pt` | 近期参照 | 原RIS最高分模型（完成第50轮），有明确来源；尚未由历史池选拔证明是综合冠军 |
| `anchor_iter34.pt` | 较早固定锚点 | 中间训练快照，用于观察跨阶段改进和退化，保留原命名 |
| `anchor_iter19.pt` | 更早固定锚点 | 与中间快照拉开训练阶段，避免只学会克制单个近期对手；不是强度排名第三的证明 |

每逢评估间隔，候选对上述每个模型各100局，同洗牌换色，各自报告区间。
这三个权重是在已有可追溯快照中选定的，并非全历史锦标赛筛出的前三名。
当前候选iter62对三者尚未确认优势，所以这次只改变搜索基准，没有替换任何权重。

维护流程如下，**程序没有自动执行冠军选拔或池更新**：

1. 长期保留iter19/iter34两个锚点及其结果；`best.pt`/`latest.pt`不能直接作为可变池成员。
2. 日常评估出现改善信号时，冻结候选，另用未参与调参的种子、预先固定的局数和判断标准，
   与近期参照直接对战；同时检查旧锚点表现，不能只凭一次100局点估计或RIS高分替换。
3. 确认要更新近期参照后，将新权重保存为新的只读用途快照、计算SHA256、保留来源，
   新建带新id的池清单，再在下次运行切换 `--eval-pool`。旧清单、权重和结果继续保留。
4. 新旧池的近期参照曲线分开；长期锚点在相同搜索/种子协议下可用于连接趋势。
   新的1600/16基准仍需建立自己的基线，不能直接连接旧800/64得分。

Pika是独立外部挑战，不参与这三个权重的滚动替换；其版本、节点预算固定，需改变时另立基准。
以上只影响评估，自博弈仍由最新模型生成，不把历史对手或Pika混进训练采样。

## 训练内使用

下列参数使用自己创建的 `data/eval/my_pool.json`；后面的轮次和生产配置是原工作区的历史说明，
不应作为新公开项目的默认续训配置。

在核对过的原续训命令上增加以下参数；**这是一段附加参数，不是完整续训命令**：

```text
--eval-pool data/eval/my_pool.json --eval-games 100 --eval-mcts-simulations 1600 --eval-leaf-batch-size 16 --eval-interval 5 --eval-seed 2026102202
```

- 当前生产在零基 iteration=62，间隔 5 时下一次评估在完成第 65 轮后。
  每个对手各 100 局，一次共 300 局，开销高于原来的单对手 100 局；本次没有启动续训。
- 续训必须保留原学习/采样配置。最新 run 为 1120 局/轮、普通1600/强3200模拟、
  leaf16、去重关、1250更新步、buffer容量6M、LR5e-5、cosine总计划2000轮，
  与旧 README 里的默认值不同。先用 `tools/run_status.py` 核对；仅增加评估参数不需重置优化器。
- 评估默认1600模拟/叶批16。独立CLI用 `--leaf-batch-size`，训练用单独的
  `--eval-leaf-batch-size`，不改变自博弈叶批。叶批会改变批内搜索调度，应作为搜索基准的一部分记录。
  历史池双方仍为去重开、虚拟损失3、无根噪声，机会配置继承训练 `chance_nodes/chance_k`。
  本次只调整模拟数/叶批，未跟随训练的去重关闭；因此与实际训练搜索并非全部参数一致。
  RIS旧路径也应用 `eval_leaf_batch_size`，其他设置仍沿用旧路径的训练配置。
  `--quick`仍是50局/400模拟的RIS短检查，叶批默认16，不是日常1600模拟基准。
- 训练启动前验证清单，每次评估重验清单与权重。评估使用网络副本，退出或异常时恢复
  Python/NumPy/Torch/CUDA 和自博弈 RNG；串行也不会因为加载历史模型而消耗训练随机流。
  从旧 RIS 路径切换到池会去掉旧路径消耗的一次训练 RNG 抽种子，不承诺与旧路径逐位相同。
- `eval_seed` 固定同一日常种子集，便于跟踪；不能反复调参后把它称为独立验收。
  池/预算/代码变化应分开比较。正式晋升另行事先固定留出种子、局数及多重比较政策。
- 每轮单独保存 `eval/pool_iter<索引>_<唯一ID>.jsonl` 及完成哈希；`train_eval.jsonl`
  追加 `type=train_eval_pool` 索引，各对手摘要也进入完整检查点。没有总平均分或自动冠军门控。
  评估引用训练 attempt；评估完成不等于训练提交成功，中断后旧输出保持未确认，重试另建文件。
- `--eval-max-plies` 默认600，未终局整对排除。置信区间退化时日志显式标记，不据此确认优势。
  `--eval-games 0` 停用评估。未指定池仍运行旧 RIS 回归；默认也不更新 best。
- 全新训练在只报告策略下可能没有 `best.pt`，GUI/独立评估可选择 `latest.pt`。
  旧检查点已提交的 best 导出若被中断，恢复时仍会修复，不能误当作新的晋升。

Pika 暂不加入训练周期或自博弈采样；用下节命令做较低频外部挑战。

## Pika 接入与边界

通过 `--pika-exe "<PIKA_EXE>"` 指定自己准备的兼容可执行文件完整路径；
`<PIKA_EXE>` 是占位符。仓库不提供、下载或自动安装该引擎。历史实验使用 `jieqi_old` 构建。
普通象棋发行版及缺少匹配网络的揭棋 NNUE 版本不能替代该构建。
可执行文件及其 SHA256、限制类型、线程、Hash、超时和桥接版本进入 run manifest。
每局使用新引擎进程，避免换色时携带另一方的私有信息或跨局 Hash 状态。

```powershell
python tools/eval.py --model data/models/latest.pt --opponents "pika:10000,pika:100000" --pika-exe "<PIKA_EXE>" --pika-limit nodes --games 100 --sims 1600 --leaf-batch-size 16 --workers 4 --seed 2026102202
```

`pika_engine.py` 的输入来自 `belief.info_state(state, state.side)`：

- 明暗棋盘、行动方和当前玩家的类型计数信念；不读取环境真实池、预洗牌真值或
  真实对手的私有信念。被吃方不知道的暗子类型继续留在计数上界中，不随机猜出后当真。
- 使用 Pika 的“剩余池”FEN，马/象为 `N/B`；项目原有 FEN 使用 `H/E` 和被吃计数，
  不能把 `jieqi.to_fen(state)` 直接传给 Pika，它还会包含来自真实池的私有信息。
- 每步 `searchmoves` 只传项目裁判允许的着法，返回着法再次核验。实际移动、揭示、
  重复/无吃子/长将/长捉和终局判定由项目裁判执行。
- **内部搜索规则仍是 Pika 自身规则。** 当前局面 FEN 不能表达项目的完整规则历史，
  该分支也不使用传入的无吃子计数作为项目规则时钟；每步重建 FEN 会丢失其内部历史。
  因此这里评估的是“Pika 在项目裁判和根合法着约束下”的对手强度，不能声称两个
  引擎的内部历史规则完全一致。Pika 的不完美信息近似也不是项目搜索的实现替代。
- 崩溃、超时、网络加载错误、非法/空 bestmove 均中止运行，不计成棋力输赢，
  不静默回退随机着法。正常结束和异常路径都会关闭所属引擎进程。

并行评估按任务完成情况检查错误，成功结果仍按原配对顺序写入。任一任务失败或主进程
收到中断时，取消排队任务并终止本次评估的 worker 及其引擎子进程；不等待其他完整对局，
不终止无关子进程。Windows 使用每个 worker 自有的 Job，POSIX 使用独立进程组。
失败输出保留已写记录，不生成完成标记；训练内历史池使用同一退出路径。

`--pika-timeout` 为每次协议响应的上限，默认 30 秒；应大于每步 movetime。
节点限制由引擎自身执行，可能因其检查粒度超出预算；逐局记录引擎报告的累计节点数。
不要把 MCTS 的模拟数直接等同于 Pika 的节点数。固定节点适合重复测试，等时间比较
应另行隔离机器负载并固定硬件、并发数和线程数；同时运行的评估耗时不是等时间棋力结论。

## 统计与记录

评估协议仍为 v2：同洗牌换色、环境/双方搜索独立随机流，任一局未终局则剔除整对。
独立评估的统计输出新增 `statistics_version=2`：

- `score` = 有效完整配对内的 `(胜 + 0.5 × 和) / 局数`。
- `bootstrap_ci95`：按**整对均分**重采样 20000 次的 percentile 95% 区间。
  统计使用独立 RNG，不消耗对局随机流；`bootstrap_seed` 记录统计种子。
- `pentanomial`：每对总得分 0 / 0.5 / 1 / 1.5 / 2 的五个计数。
- `bootstrap_degenerate`：空样本、单配对或所有配对均分相同时为 true。
  此时 bootstrap 没有足够的经验分布变化，零宽区间不能用于证明优势或精度。
- 兼容字段 `ci95_low/high` 仍为旧的近似 Wilson 区间；新增 `wilson_ci95_approx`
  明确其性质。正式报告优先使用配对区间，不能把单局近似区间当配对检验。
- 逐局保存 `move_seconds`、`moves_played` 和 Pika 元数据；耗时含通信，
  不含引擎初始化。摘要的累计耗时含被剔除的未终局对局，仅作资源诊断。
- 运行头、manifest和每个摘要记录实际 `leaf_batch_size`/`leaf_dedup`；训练索引也记录模拟数/叶批。
  `tools/ab_runner.py` 的旧实验缺省显式保持leaf64，可在实验spec中设置 `leaf_batch_size`。

离线统计与在线摘要使用同一配对 bootstrap 实现；指定相同种子和重采样次数可复现：

```powershell
python tools/paired_stats.py <evaluation.jsonl> --seed 2026102201 --bootstrap 20000 --out <new-stats.json>
```

离线总胜/和/负、颜色分层与配对统计现在都只使用完整有效配对。
缺色、重复记录、不同 seed 或未终局配对不会混入总得分。输出路径必须不存在。
多对手和反复检查会带来多重比较问题；多个探索性区间不能自动视为整体冠军检验。
